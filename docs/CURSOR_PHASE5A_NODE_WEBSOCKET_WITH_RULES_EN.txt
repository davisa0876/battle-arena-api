5. LARAVEL ↔ REDIS ↔ NODE SECURITY CONTRACT

A. Existing web session / mobile bearer -> authenticated HTTP request:
   POST /api/realtime/tickets (Sanctum, web CSRF, throttle, no-store).
B. Laravel generates opaque 256-bit ticket, stores SHA-256(ticket) in a
   dedicated Redis key with TTL ~30 seconds (SET NX EX or equivalent).
   Store only minimal player id and issue metadata; never raw ticket.
C. Response sends one-use ticket, `expires_in`, public `ws_url` obtained from
   configured PUBLIC_WS_URL; browser/mobile must never receive `realtime:3001`.
D. WS upgrade: /ws?ticket=opaque; validate method/path/header/Origin, token
   encoding/length and limits BEFORE any Redis lookup; never log full URL.
E. Node consumes SHA-256 key with atomic GETDEL. Exactly one succeeds,
   even with concurrent attempts and multiple service instances.
F. Only after redemption and identity binding accept the upgrade and emit
   protocol v1 `connection.ready` with server-derived player_id and connection_id.
G. Reject invalid/expired/reused tickets, foreign Origins and Redis outages;
   no anonymous fallback; never accept `player_id` from the client.
H. Bound socket lifetime and document logout/token-revocation limitations.

Implement the SAME namespace/TTL/serialization on both sides. Verify this
using an actual Laravel -> Redis -> Node end-to-end test, not only mocked tests.
Use wss:// and strict proxy logging/Origin policy outside isolated local dev.
