PRIMARY GOAL
Build a production-minded, server-authoritative, deterministic and fully tested two-human PvP battle backend, starting from an accepted PRIVATE ROOM with two distinct trainers. The two players must be able to select owned creatures, lock readiness, enter exactly one battle, alternate attacks and defenses, and finish on KO with exactly-once PvP XP. All game commands remain Laravel REST. Node only relays versioned change notifications to authorized subscribers.

CRITICAL ARCHITECTURE RULES — NEVER VIOLATE
1. Laravel is the ONLY authority for authentication, room membership, eligibility, moves, defense, turn order, damage, HP, PP, stamina, RNG, winner/loser, XP and state persistence.
2. PostgreSQL is the durable source of truth. Redis stores ephemeral auth and notification transport only.
3. Node.js must NOT query Postgres directly, calculate combat, receive battle actions over WebSockets, or decide who wins.
4. Reuse existing pure PHP combat value objects and calculations. The existing BattleState/BattlePhase/BattleEngine are currently PvE-specific. Do not force a human PvP turn loop into AI-only transitions; design a PvP-specific state machine and extract neutral pure combat calculation if necessary.
5. Preserve PvE behavior, tests and APIs; do not introduce a duplicated second damage formula.
6. Use Laravel Sanctum for ALL protected PvP REST endpoints, with per-resource authorization and cross-user isolation.
7. Two players MUST be different users, with independently verified owned creatures; never trust a client-supplied player_id, defender_id, winner, HP, XP or battle snapshot.
8. Idempotency and optimistic version checks must be enforced in database transactions and backed by appropriate unique constraints; no double-spend of PP/stamina or double-award of XP.
9. Apply reliable SQL locking order to prevent deadlocks. Real PostgreSQL concurrency tests are required.
10. WebSockets are best-effort hints ONLY. REST GET state and events support reconnect, rehydrate and recovery. Publish only after committed DB transactions.
11. Do not implement matchmaking, ranking, seasons, spectator mode, public lobbies or full combat UI.
12. Do not auto-forfeit or auto-award XP because of socket disconnect in Phase 5B.2; define disconnect policies only in Phase 5B.4.
13. Do not enable features.pvp = true yet.
14. No destructive migrations, no compose down -v, no volume deletion, no APP_KEY rotation, no automatic commits/pushes, no new remote repository.

ACCEPTANCE GATES
A. Two independent authenticated level-6+ users can join an accepted private room and each select an OWNED creature.
B. Both ready => exactly one battle, persisted and discoverable on refresh.
C. Human A attack -> Human B defense -> Human B attack -> Human A defense, with a deterministic swap and correct damage/HP/PP/stamina.
D. Valid recover-skip switches actor immediately; basic strike only at zero move PP.
E. Stale, forged, duplicated or out-of-turn requests cannot mutate battle, bypass ACL or duplicate rewards.
F. Server-side KO persists winner/loser; +20 / +10 XP once, correct for both host-wins and guest-wins cases.
G. WebSocket notification is hint-only, targeted and versioned; Redis/Node failure does not corrupt REST combat.
H. PvE and 5B.1 regressions remain green. PostgreSQL concurrency tests run or their precise environment limitations are disclosed.
I. Public features.pvp is still false; no matchmaking/UI creep into 5B.3/5B.4.
